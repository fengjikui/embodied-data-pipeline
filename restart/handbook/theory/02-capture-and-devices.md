# T2：设备、人员、遥操作与数据来源

读完应能说明：哪个设备运行什么程序，操作员如何完成一段记录，以及“开源／仿真／遥操作”为什么不是互斥分类。

## 数据来源按不同维度分类

| 维度 | 例子 | 对使用的影响 |
| --- | --- | --- |
| 获得方式 | 公开下载、采购、自采、合作 | 授权、可追溯来源与费用 |
| 所处环境 | 真实世界、物理仿真、程序合成 | 真实偏差、接触可信度、能否代表部署环境 |
| 生成者 | 人遥操作、拖动示教、已有控制程序、策略探索 | 标签来自谁、是否成功、覆盖什么状态 |
| 数据内容 | 视频、深度、状态、动作、力、工艺结果 | 能支持哪些训练或评估目标 |
| 本体与任务 | G1 装配、Franka 抓取、自研工站 | 控制接口和动作语义是否兼容 |

因此，一个公开数据集可以同时是“仿真环境中采集的遥操作数据”。遥操作是一种采集方式，LeRobot 是一种数据组织与访问规范，二者不能放在同一层互相替代。

## 宇树 XR 真机采集的默认分工

XR（Extended Reality，扩展现实）在此指支持跟踪与交互的头显。下面按官方外置 Host＋机器人 PC2 方案说明，实际 G1 到货后核对配置。

| 设备／程序 | 运行位置 | 工作 |
| --- | --- | --- |
| 头显浏览器与 XR 页面 | 操作者佩戴的头显 | 显示机器人画面，输出头／手腕／手指或手柄跟踪 |
| `teleimager-server` | 机器人开发计算单元 PC2 | 读取相机、提供图像流 |
| `teleop_hand_and_arm.py` | 外置计算机 Host | 接收跟踪、逆运动学与手部映射、控制通信、录制 |
| 机器人控制系统 | 机器人内部 | 执行目标、反馈状态；手部可能有额外服务 |
| 训练程序 | 后续的本地或服务器环境 | 读取整理后的数据、优化模型参数 |

Host 是外置主机的名称；PC2 是官方方案中开发计算单元的标识。机器人内部计算不应笼统视为一个没有分工的电脑。图像路径按服务配置可直达头显或提供给 Host；动作控制与数据录制是另一条链路。[宇树默认部署与代码结构](https://github.com/unitreerobotics/xr_teleoperate)

## 操作人员如何配合

工程人员先完成网络、驱动、软件版本、坐标与初始姿态、工具与相机检查。采集时建议一名示范者和一名现场协助者：前者完成任务，后者负责记录控制、复位物料、观察状态与停止操作。角色可由现场流程安排，不是官方规定必须招聘多少人。

在官方默认键盘流程中，打开录制模式后，`r` 开始遥操作，`s` 开始录制，再次 `s` 结束保存一个 episode。Episode（轨迹／回合）指从规定开始条件到结束条件的一段操作，不一定等于一个视频文件。

## 仿真有什么变化

仿真程序产生虚拟机器人的图像、状态和物理交互，接收相同或相近形式的控制目标。头显依旧可以由人操作；也可以由脚本或训练策略产生动作，后两者不自动称为人的遥操作数据。

物理仿真会计算运动、接触等近似规律；本手册生成正弦数值与小图片的实验没有物理引擎，属于教学合成，不是 G1 仿真。

MIRAI 展示的另一种采集方式是手把手引导机械臂，由配套相机和系统生成技能。其硬件和应用支持范围需按产品文档确认。[MIRAI 示教说明](https://www.micropsi-industries.com/blog/how-to-train-your-mirai-system)

## 相机、本体和工具改变时

需检查观测分布、标定、动作定义、接口和技能有效范围。MIRAI 16.1 指南对某项技能的相机设置有固定要求；这是该产品的约束，不代表所有研究模型都无法跨视角泛化。[厂商指南](https://micropsi.industries/user-guide/Quick-Start-Guide-UR.pdf)
