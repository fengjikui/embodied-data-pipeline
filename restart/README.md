## 1. 本轮工作的原则

暂停此前的任务推进，从需求、理解和用户实际操作出发，重新建立工作主线。

此前的文档、代码和研究结果只作为参考材料。旧实现不自动成为新系统的架构约束，旧报告里的结论也不自动视为本轮已验证的事实。需要引用时，应说明来源、适用条件及是否需要更新。

新一轮内容统一放在 `restart/` 独立目录。当前先保留旧目录和 Git 历史，不执行删除、搬迁或覆盖。后续若清理旧工作区，应先核对已提交、未提交和被 Git 忽略的文件；Git 历史只能恢复已经纳入版本管理的内容，不能保证恢复本机所有文件。

本阶段先整理意图和问题，再逐项学习、核实与实验。不要在需求尚未清楚时，继续堆积大篇幅报告或直接沿用旧系统进行开发。

## 2. 最终希望获得的交付

### 交付一：自己真正理解并能清晰汇报

围绕“搬箱子”和“打螺丝／装配”两个具体案例，理解并能够讲清楚：

数据采集 → 真机或仿真遥操作 → 数据整理与转换 → 训练样本构造 → 模型训练 → 部署 → 实际推理与控制 → 运行结果回流。

学习应深入关键代码和核心数据流。最终应能回答：每一步的输入和输出是什么、由哪台设备执行、关键代码做了什么、为什么需要这一步，以及如何判断该环节已经跑通。

### 交付二：普通人也能操作的数据管线产品

开发带 UI 的跨平台系统，让没有技术背景的人能够完成常见操作。使用者应清楚知道当前要做什么、系统在做什么、何时完成、出错后如何恢复。

例如：选择机器人和采集任务，检查设备连接，开始遥操作与录制，查看采集结果，整理和转换数据，创建训练任务，检查训练产物，并在具备条件后进入部署和运行流程。

“便捷”不能只体现为增加一个按钮，还应包括设备准备、连接检查、参数预设、运行状态、错误提示、停止与恢复，以及结果可追溯。

### 交付三：与理解和产品一致的专业报告

将已核实的知识、案例、关键代码解释、产品流程和实验结果整理为可用于主管汇报的材料。报告应便于讲述和展示，明确区分已验证结果、公开资料描述、技术推断和后续计划。

## 3. 研究与实践的背景

- 所在团队是集团内部 AI 实验室，正在探索工业具身智能方向。
- 实验室当前尚无确定的产线落地方向，现阶段可承接产线提出的改进设想，后续也会主动开展现场调研。公开讨论以电子与机械制造的匿名共性问题为范围，不要求披露企业具体产品和工艺机密。
- 当前已明确的本体方向为宇树 G1 EDU；手部、相机及力传感器等具体配置尚未确定。
- G1 EDU 是首个实践对象。未来可能按产线需要采购电机并自研机械结构，接入非人形、异构的专用机械臂，以及与传统自动化设备协作的工站。
- 市面可采购的末端执行器和传感器均可作为候选，但需要比较实际任务适配、集成难度和数据需求。
- 用户具备 Transformer、LLM 训练和部分强化学习基础，希望通过命令、少量关键代码和实际操作补齐机器人领域知识。
- 实际数据与训练环境将考虑公司内网，以及 Linux／Ubuntu 和 Windows；本机无需大量下载数据。
- 不以赶截止日期为优先，按事项逐项完成、理解和验证。

## 4. 需要逐项弄清楚的问题

### 4.1 用两个完整案例贯通流程

案例 A：机器人搬箱子。
案例 B：机器人取螺丝、对准装配位置，并配合或使用电动工具完成装配。

对每个案例，逐项说明：

1. 实际任务如何拆分，成功标准是什么。
2. 哪些环节使用传统控制、任务编排、监督学习或强化学习。
3. 如何在真机与仿真中采集数据，遥操作员实际如何操作。
4. 原始数据包含哪些传感器观测、机器人状态、动作、时间信息和任务结果。
5. 数据如何存储、检查质量、转换、划分和管理版本。
6. 模型实际读取什么样的样本，训练输出什么产物。
7. 推理时输入来自哪里，输出如何交给控制器和机器人执行。
8. 失败、人工接管和任务结果如何进入下一轮数据与训练。

### 4.2 遥操作的设备与操作流程

用户目前听到的“三台设备”配置需要结合实际方案核实，不预设所有遥操作都必须恰好使用三台设备。

需要画清楚并解释：操作者使用的设备、运行遥操作／采集程序的计算设备、机器人本体、仿真设备及网络之间的关系。分别说明软件装在哪里、谁向谁发送什么、谁负责记录、谁负责控制。

从用户视角梳理完整操作：准备设备 → 连接与校准 → 选择任务 → 开始控制与录制 → 停止 → 检查与保存。真机和仿真分别说明，并标出可以自动化与需要人工操作的步骤。

### 4.3 模型与训练机制

用户提到的“当前五种策略”先作为待明确的研究范围，后续确定具体指哪些策略及代表模型，避免自行套用旧报告中的分类。

每一种方法均按同一套问题说明：

| 维度 | 需要弄清楚的内容 |
| --- | --- |
| 模型结构 | 主要模块、各模块输入输出、是否包含视觉语言骨干或动作模块 |
| 数据与样本 | 文件格式、字段、单位、坐标系、时序窗口及实际张量形状 |
| 监督学习 | 标签是什么、标签来自哪里、损失函数优化什么 |
| 强化学习 | 环境、状态、观测、动作、奖励、终止条件和算法 |
| 训练过程 | 数据读取、前向计算、损失、参数更新及检查点 |
| 推理过程 | 输入预处理、模型输出、动作后处理和控制器接口 |
| 适用范围 | 所需数据、硬件条件、适合的任务及已知局限 |

同时梳理世界模型用于具身智能的进展：模型预测什么、消费何种数据、采用何种结构与训练目标，以及在仿真、规划、策略学习或数据生成中具体承担什么角色。

最新进展需要注明查证日期和一手来源，并区分研究演示、公开可复现成果与实际生产应用。

### 4.4 行走、多地形与全身协同

弄清楚强化学习训练双足行走和四足多地形运动的完整流程，包括仿真环境、地形设置、奖励、策略结构、训练数据产生方式、实机部署及推理控制链路。

进一步解释“全身工作场景”如何实现：移动、站稳、伸手、抓取、持物、施力之间如何协调；是否独立训练，如何组合，以及控制权、坐标系、频率和约束如何衔接。

这部分应最终能够通过命令、关键代码或可观察的实验理解，不能仅停留在概念图和术语上。

### 4.5 典型厂商、生产能力与通用性

覆盖宇树、智元、银河通用、Figure、Tesla Optimus，以及研究中发现有价值的其他厂商。

对各家分别核实：

- 已公开展示和已实际投入生产的能力分别是什么，有何证据。
- 数据采集、存储、转换、训练和部署的公开流程是什么。
- 哪些格式、模型或实现细节公开，哪些尚无法确认。
- 数据能否在不同管线之间转换，需要满足什么语义与硬件条件。
- 商用或开源模型能否跨本体使用，需要适配哪些部分。

特别验证“不同机器人是否只需要改变输出关节数量”这个理解。比较时需要检查观测、动作语义、关节与末端结构、坐标与标定、控制接口、动力学和任务分布等因素，不把文件格式相同视为直接可训练或可部署。

### 4.6 开源数据集究竟如何被消费

对有价值的数据集建立可查询索引，并逐项回答：

| 项目 | 需要说明的内容 |
| --- | --- |
| 来源 | 提供方、采集方式、真实／仿真、版本和许可 |
| 内容 | 本体、任务、传感器、状态、动作及任务结果 |
| 格式 | 存储结构、字段含义、时间关系及样本示例 |
| 实际用途 | 被哪些模型、训练阶段或评估任务消费 |
| 接入等级 | 可读取、可转换、可用于指定模型训练，分别需要什么条件 |
| 不适用原因 | 字段缺失、动作语义不同、本体差异、许可或其他限制 |
| 替代价值 | 无法直接训练 G1 时，是否可用于感知、预训练、仿真或其他本体 |

“能够下载”“能够打开”“能够转换文件”“适合目标模型训练”“能在 G1 上有效运行”需要分别判断。对不能直接使用的数据，也要说明其原本的合理用途。

### 4.7 自研本体与传统自动化结合

研究范围包括专用机械臂、直线轴、夹具、供料器、拧紧工具和已有自动化工站。比较它们与 G1 数据管线的共性，以及本体描述、设备接口、动作语义、工艺事件和质量记录的差异。

将“学习能力与传统自动化结合可能适合集团产线”作为待验证的路线假设，结合节拍、质量、变化适应能力、成本与维护条件评估，不预设人形或 VLA 是所有任务的必选方案。

首版应跑通一个限定配置，同时为不同设备、本体和模型保留明确接入接口。扩展能力通过后续第二类设备的实际接入验证，不只依赖架构图。

### 4.8 专项能力突出的企业与研究案例

除大型机器人厂商外，补充羽毛球对打、工业视觉引导、学习式装配等专项案例。研究它们如何组合感知、预测、规划、学习与控制，以及数据被各个环节如何使用。

展示效果、纪录认证、厂家宣称的量产能力和独立生产验收需要分开记录。技术资料没有公开的部分标记为未知，不根据视频反推具体模型或训练算法。

## 5. 可视化产品需要从实际使用者出发设计

在上述知识逐步贯通之后，再确定产品架构和技术选型。

初步需要覆盖的用户流程是：设备与任务准备、真机／仿真采集、数据导入、质量检查、整理与转换、版本发布、训练任务、产物检查，以及后续具备条件时的部署与结果回流。

跨平台需要分别明确 UI、采集端、训练端、机器人控制端支持什么系统，不预设每个组件都能在所有平台运行。还需考虑多设备连接、内网运行、安装升级、配置迁移和新版本发布。

兼顾未来扩展的方式是保留设备适配、本体配置、任务／工艺定义和模型导出的边界，首版优先完成真实可用的最小流程。具体分层是设计候选，需经需求与实验验证后确定。

每项功能的验收都应从使用者能否独立完成操作出发，同时明确哪些环节仍依赖机器人、传感器、驱动、训练硬件或现场配置。

汇报主要面向集团一级 AI 实验室主管，后续可用于实验室同事交流，也可能面向董事长等更高层管理者。材料按业务判断、路线与证据、可演示流程、技术附录组织，依据受众调整深度。

## 6. 接下来的合作方式

1. 先一起确认本初稿，逐步明确概念范围与案例边界。
2. 每次围绕一个具体问题，采用简短解释、实际数据或代码示例，再由用户复述理解。
3. 将核实过的知识和跑通过的步骤记录下来，逐步形成完整案例。
4. 从案例中提取真实用户操作，设计可视化产品的流程与验收要求。
5. 分阶段实现产品，并让用户实际操作、反馈与验证。
6. 最后形成与实际系统一致、用户能够独立讲述的汇报材料。
