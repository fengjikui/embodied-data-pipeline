# 四项能力与上下身协同：为什么不能直接拼两个模型

## 1. 四项能力不是四个必选神经网络

| 能力 | 回答的问题 | 典型输入 | 输出到哪 | 验收 |
|---|---|---|---|---|
| 运动控制 | 怎样站稳、走、转身 | 关节、IMU、基座速度/姿态、运动命令 | 关节目标/力矩到低层控制 | 跟踪、失稳、跌倒、能耗 |
| 导航 | 往哪走、怎样避障到工位 | 定位/地图、目标、相机/深度、障碍 | 速度/路径给运动控制 | 到达、碰撞、接管、停靠 |
| 操作 | 怎样抓、放、对位、用工具 | 视觉、语言、双臂/手状态、接触 | 手臂/手/工具参考 | 物品和工艺质量 |
| 全身协同 | 身体如何支持操作与持物移动 | 全身状态、手臂参考、接触、负载、目标 | 一致的全身参考/执行动作 | 负载稳定、碰撞、可达性 |

这是功能划分。同一个模型可以覆盖多项，一项也可能由规划器、网络和控制器共同实现。原报告的四项能力不意味着要训练四个 VLA。

“下半身 PPO”和“上半身 BC/VLA”是起点，不是系统的完整接口。手伸到远处、工具反扭矩、持物质量都会改变重心和接触力；腰关节常属于双方都想控制的共享区域。

## 2. 三条组合路线

### 路线 A：分阶段执行，先获得可解释基线

导航到工位 → 确认稳定站立 → 允许上肢策略执行 → 工具完成与质量复核 → 恢复移动。一次只有一套有明确关节权限的控制链。先测固定工位取放/对位，再扩展工具。这是实验室首轮建议，不能覆盖边走边装配。

使用出厂/已有控制器并不要求实验室重新训练行走。实机接口是否允许上肢控制叠加、哪些关节可写、控制模式如何交接，必须依据采购配置与 SDK 实测确认。

### 路线 B：分层策略＋全身控制器

任务层选择工位/技能；导航给移动目标；操作策略给双手 TCP/关节/运动参考；全身控制器统一跟踪，保持接触和平衡。全身控制器可用优化、RL 或混合方法，不是只能用 VLA。

优化式 WBC 的思想可以写为：最小化手部与基座跟踪误差、姿态和动作变化，满足机器人动力学、足部接触、摩擦、关节限位等约束。示意动力学 `M(q)qdd + h(q,qd) = S^T*tau + J_contact^T*f_contact`。真实约束和权重要根据设备设计；本仓库没有实现该求解器。

RL 跟踪式控制器可把全身参考与实测状态输入 actor，输出一致的关节命令。上层学习模型的标签必须和它的参考接口相匹配，不能把关节角、TCP 或 latent 互换。

公开候选：[NVIDIA GR00T-WholeBodyControl](https://github.com/NVlabs/GR00T-WholeBodyControl) 包含 decoupled WBC 和 SONIC 线路，公开了 G1 的采集、VLA 训练与执行文档。SONIC 把运动表示与控制器配套，GR00T 的 `UNITREE_G1` 与 `UNITREE_G1_SONIC` 接口不同。**本次只核查文档，不运行该控制栈**。[GR00T 入口](https://github.com/NVIDIA/Isaac-GR00T)。

### 路线 C：联合的全身学习系统

策略根据视觉/语言与全身状态同时产生身体和手部参考，底层仍有执行与平衡机制。联合训练数据需要身体、接触和双手同步，单独桌面上肢数据不够。训练更复杂，失败归因也更难。

[Figure Helix 02](https://www.figure.ai/news/helix-02) 官方披露了任务理解、视觉动作与学习全身控制的分层系统。它是理解架构的参考；本次未确认可用于本实验室的完整 Helix 权重/训练数据，不作为 G1 可运行入口。[宇树 UnifoLM-WLA](https://github.com/unitreerobotics/unifolm-wla) 提供自己的动作专家与本体规范，仍需验证其与采购设备、控制器及任务的关系。

## 3. 最容易出问题的是接口

| 接口 | 必须说清 | 错了会怎样 |
|---|---|---|
| 关节权限 | 哪个进程控制腿、腰、臂、手；仲裁与切换 | 两个进程互相覆盖命令 |
| 坐标 | world/base/body/flange/tool，左右手，四元数顺序 | 对位方向错、目标不可达 |
| 动作含义 | 绝对/增量、角度/速度/力矩、TCP/latent | 文件能读却执行完全不同 |
| 时间 | 捕获时间、推理延迟、参考开始时间、有效期 | 跟踪过期目标、忽快忽慢 |
| 负载 | 工具/物品质量、重心、惯量、反力矩 | 空载稳定、持物失稳 |
| 接触 | 双脚、手、工件/工具的接触与状态转换 | 操作干扰平衡或错误退出 |
| 控制器版本 | 参考维度、归一化、增益、历史与 latent decoder | 上层模型与底层接口不兼容 |

时频示意：操作策略每隔一段时间生成动作块，全身控制器更频繁更新，电机伺服再跟踪。实际频率依上游与设备确定，不给 G1 EDU 猜默认值。上层块的时间跨度必须与执行频率匹配，例如 H=8、训练采样20Hz覆盖约0.4秒；这不能直接拿去按50Hz解释。

## 4. 螺丝装配如何具体配合

第一阶段用固定工位＋稳定站立控制。让上肢完成取料与工具接近，验证工艺和工具接口。第二阶段添加身体/腰姿态以扩大可达空间，统一两臂与身体参考。第三阶段再研究持工具移动，加入负载和惯量，并在移动和操作阶段之间管理接触/姿态。

“固定站位”不是随意关闭腿控制；腿仍由已确认的站立/平衡控制链负责。工具拧紧的反扭矩不能只在手指数据里体现，需要日志和控制器共同处理。

## 5. 数据怎样支撑协同

上肢示范：双臂/手的联合命令、实际状态、视角、语言。行走 RL：仿真器中的状态/命令/动作/奖励、终止、动力学随机化与模型版本。导航：定位/地图、目标、路径/速度、障碍与接管。全身操作：身体与手部同步参考、接触、负载、控制器执行与任务结果。

这些可以存在同一个 session 中，用不同视图供不同训练器；不能把 PPO 的 rollout 强行变成“每帧有专家正确动作”的 BC 标签。人动作捕捉经 retargeting 后可以提供运动参考；它仍需目标机器人可达性、碰撞、平衡与动力学验证。

## 6. 世界模型能帮哪里

世界模型预测动作后可能发生的状态/图像/latent，可辅助候选动作规划、任务进展判断、数据增广或模型式 RL。动作条件、预测跨度与接触可观测性决定它能回答什么。

对螺丝场景，可研究“会不会撞、是否接近、哪个候选动作更可能进入下一阶段”；视觉生成很像不等于准确模拟螺纹摩擦、打滑、反扭矩与质量。需要用真实工具结果校验预测，不能把世界模型视频当拧紧验收。[宇树世界模型动作项目](https://github.com/unitreerobotics/unifolm-world-model-action)、[1X 世界模型说明](https://www.1x.tech/discover/redwood-ai-world-model)。

## 7. 最短学习顺序

先把四项能力各用一句话解释 → 画出任务层/策略/控制器/电机 → 从 BC 预测看到动作还原 → 看 PPO actor 的输入输出 → 读 G1 上游控制接口 → 才讨论两者连接。详细命令见 [实操](22-command-learning-lab.md)。
